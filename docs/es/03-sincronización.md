# 3 · Sincronización

**Sync** construye (o refresca) la biblioteca reproduciendo el generador
oficial de la web. Es la parte más sutil del programa, porque el objetivo no
es "un fichero de expedición válido" sino **"los bytes exactos que produciría
la web"**.

## Qué lee (entradas)

Todas las entradas son los *datos en bruto* del repositorio
[cwmonkey/nms-expeditions](https://github.com/cwmonkey/nms-expeditions),
descargados bajo demanda y **cacheados** en `data/sources/` (ver
`sources.py`). Nada se vuelve a descargar de la red en cada sync: una fuente
se re-descarga solo si lo fuerzas o si aún no está cacheada.

El generador consume, por combinación:

1. el JSON **base** de temporada de esa expedición+versión (el "fichero
   original" con el que empieza la web),
2. el **preset de dificultad** (Defaults = ninguno, Easy / Hardcore = un
   paquete de sobreescrituras de parámetros),
3. los **parches de versión** (nivel expedición + nivel versión, solo los
   marcados `checked: 1`, en el orden exacto de la web),
4. los **parches globales** (marcados `checked: 1`, aplicados a todo
   fichero),
5. opcionalmente, tus **sobreescrituras personales** (`overrides.json`,
   aplicadas *al final*).

Se apilan **en exactamente el mismo orden que usa la web**, de modo que el
resultado coincide.

## El pipeline de generación

Para un `(expedición, versión, dificultad)`:

```
JSON base (dict)
  → aplicar sobreescrituras del preset   (build_overrides / apply_overrides)
  → aplicar parches de versión (checked) (retirar / añadir / sustituir)
  → aplicar parches globales  (checked)
  → aplicar overrides.json personales (si existe)
  → serializar a JSON **exactamente como JSON.stringify de JavaScript**
  → escribir en ExpeditionManagerLibrary/<Mode>/<Difficulty>/NN_Name/…JSON
```

El paso de serialización es la clave. Ver la siguiente sección.

## Por qué la identidad byte a byte es difícil (y cómo se mantiene)

Un fichero JSON *semánticamente* igual no es *byte* igual. Varias cosas
difieren entre "un dict de Python con `json.dumps`" y "lo que emite el
JavaScript de la web":

- **Formato de números.** `JSON.stringify` de JS escribe `1.0` como `1` y
  tiene un umbral concreto para pasar a notación exponencial
  (`1e-6 … 1e21` usa decimales planos). El `repr` de Python cambia de punto.
  `sync.py` reimplementa las reglas de números de JS (`_as_js_numbers`,
  `_float_js_str`) para que `1.0` → `1` y los exponentes coincidan.
- **Orden de las claves.** La web conserva el orden de inserción del objeto;
  el generador debe aplicar los parches en la misma secuencia para que las
  claves caigan en las mismas posiciones.
- **Escapado de cadenas.** JS escapa un pequeño conjunto concreto de
  caracteres; el escritor replica esa tabla de escapes.
- **La línea de crédito.** La web inyecta una línea
  `"_generatedBy": "Generated by https://cwmonkey.github.io/nms-expeditions/ …"`.
  El generador inyecta la *misma* línea para que el hash cuadre.
- **Marcadores `[[append]]`.** Los parches usan marcadores que se retiran de
  la misma manera que los retira la web.

El resultado neto: para una combinación estándar (sin sobreescrituras
personales), el fichero en la biblioteca es **byte-idéntico** a la descarga
de la web. Esa es la garantía estrella del programa (ver
[Visión general](01-visión-general.md#invariantes-que-protege-todo-el-diseño)).

> Verificado en concreto: generar `Defaults`, `Easy` y `Hardcore` de una
> expedición a partir de las fuentes cacheadas produce un fichero cuyo
> SHA-256 es idéntico al de la biblioteca pre-construida correspondiente.

## Sync normal vs. forzado

| | **Sync** (normal) | **Force resync** |
|---|---|---|
| ¿Re-descarga las fuentes en bruto? | No — usa la caché de `data/sources/` | Sí — re-obtiene cada fuente de GitHub |
| ¿Re-deriva los ficheros de la biblioteca? | Solo si el hash del contenido generado difiere del manifiesto | Sí — regenera y reescribe los 126 |
| Red | Ninguna (si hay caché) | Necesaria |
| Cuándo usarlo | Primer uso / tras añadir una expedición | El repo de arriba cambió, o sospechas una caché mala |

El sync normal es **barato y seguro de correr a menudo**: recomputa cada
fichero, lo compara con el hash del manifiesto y solo escribe los que
cambiaron. Una pasada totalmente al día informa `0 downloaded/updated, 126
unchanged` y no toca la red.

## Qué significa "sin cambios" para el hash

Como `overrides.json` personal se aplica *al final*, editar tus
sobreescrituras cambia los bytes de salida y por tanto el hash — un sync
normal re-escritará esos ficheros (ya no coinciden con el hash estándar del
manifiesto). Es esperado: tus ficheros personalizados son *tu* variante. Ver
[Personalización](05-personalización.md) para la relación entre el formulario
de personalización por instalación y `overrides.json`.

## Puntos de entrada

- **GUI:** *Settings → Sync all* / *Force resync* (barra de progreso abajo).
  Ver [La GUI](06-gui.md).
- **CLI:** `./run.sh sync` (o `--force`, `--exp eNN`). Ver [La CLI](07-cli.md).

Ambos llaman a la misma función de `sync.py`, así que hay un único camino de
código para la generación, sea cual sea la interfaz.
