# 3 · Synchronization

**Sync** builds (or refreshes) the library by reproducing the official
website's generator. This is the most subtle part of the program, because the
goal is not "a valid expedition file" but **"the exact bytes the website
would produce"**.

## What it reads (inputs)

All inputs are the *raw data* of the upstream
[cwmonkey/nms-expeditions](https://github.com/cwmonkey/nms-expeditions)
repository, downloaded on demand and **cached** under `data/sources/` (see
`sources.py`). Nothing on the network is re-fetched on every sync: a source
is re-downloaded only if you force it or if it isn't cached yet.

The generator consumes, per combination:

1. the **base** season JSON for that expedition+version (the "original
   file" the website starts from),
2. the **difficulty preset** (Defaults = none, Easy / Hardcore = a bundle of
   parameter overrides),
3. the **version patches** (expedition-level + version-level, only the
   entries marked `checked: 1`, applied in the website's exact order),
4. the **global patches** (marked `checked: 1`, applied to every file),
5. optionally, your **personal overrides** (`overrides.json`, applied *last*).

They are layered in **exactly the same order the website uses**, so the
result matches it.

## The generation pipeline

For one `(expedition, version, difficulty)`:

```
base JSON (dict)
  → apply difficulty preset overrides   (build_overrides / apply_overrides)
  → apply version patches (checked)     (remove / append / substitute)
  → apply global patches  (checked)
  → apply personal overrides.json (if any)
  → serialize to JSON **exactly like JavaScript's JSON.stringify**
  → write to ExpeditionManagerLibrary/<Mode>/<Difficulty>/NN_Name/…JSON
```

The serialization step is the crux. See the next section.

## Why byte-identity is hard (and how it is kept)

A JSON file that is *semantically* equal is not *byte* equal. Several things
differ between "a Python dict dumped with `json.dumps`" and "what the
website's JavaScript emits":

- **Number formatting.** JS `JSON.stringify` prints `1.0` as `1`, and has a
  specific threshold for switching to exponential notation
  (`1e-6 … 1e21` uses plain decimals). Python's `repr` switches at a
  different point. `sync.py` reimplements JS's number rules
  (`_as_js_numbers`, `_float_js_str`) so `1.0` → `1` and exponents match.
- **Key order.** The website preserves the object's insertion order; the
  generator must apply patches in the same sequence so keys land in the same
  places.
- **String escaping.** JS escapes a specific small set of characters; the
  writer replicates that escape table.
- **The credit line.** The website injects a `"_generatedBy": "Generated by
  https://cwmonkey.github.io/nms-expeditions/ …"` line. The generator injects
  the *same* line so the hash matches.
- **`[[append]]` markers.** Patches use markers that are stripped in the same
  way the website strips them.

The net effect: for a stock combination (no personal overrides), the file in
the library is **byte-identical** to the website's download. This is the
program's headline guarantee (see [Overview](01-overview.md#invariants-the-whole-design-protects)).

> Verified concretely: generating each of `Defaults`, `Easy`, and `Hardcore`
> for an expedition from the cached sources produces a file whose SHA-256 is
> identical to the corresponding pre-built library file.

## Normal vs. forced sync

| | **Sync** (normal) | **Force resync** |
|---|---|---|
| Re-downloads raw sources? | No — uses `data/sources/` cache | Yes — re-fetches every source from GitHub |
| Re-derives library files? | Only if the generated content's hash differs from the manifest | Yes — regenerates and rewrites all 126 files |
| Network | None (if cache present) | Required |
| Use when | First run / after adding a new expedition | Upstream repo changed, or you suspect a bad cache |

The normal sync is therefore **cheap and safe to run often**: it recomputes
each file, compares against the manifest hash, and writes only the ones that
changed. A fully up-to-date run reports `0 downloaded/updated, 126
unchanged` and touches the network not at all.

## What "unchanged" means to the hash

Because personal `overrides.json` is applied *last*, editing your
overrides changes the output bytes and thus the hash — a normal sync will
re-write those files (they no longer match the stock manifest hash). That is
expected: your personalized files are *your* variant. See
[Customization](05-customization.md) for how the per-install customization
form relates to (and differs from) `overrides.json`.

## Entry points

- **GUI:** *Settings → Sync all* / *Force resync* (progress bar at the
  bottom). See [The GUI](06-gui.md).
- **CLI:** `./run.sh sync` (or `--force`, `--exp eNN`). See
  [The CLI](07-cli.md).

Both call the same `sync.py` function, so there is one code path for
generation regardless of interface.
